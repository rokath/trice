# Spezifikation: `trice bind`

**Version:** 3  
**Status:** Spezifikationsentwurf für das MVP  
**Repository-Bezug:** Branch `wip`, insbesondere `examples/PoC_bind_v2`, `internal/id`, `src` und `_test/testdata/triceCheck.c`  
**Zielgruppe:** Implementierung, Review, Tests und spätere Übernahme in die Trice-Dokumentation

## 1. Zweck und Grundidee

`trice bind` ist ein neues Subkommando und eine Alternative zum bisherigen Workflow:

```text
trice insert
Build
trice clean
```

Es verwendet dieselbe stabile ID-Verwaltung und soweit möglich dieselbe Parser- und Zuordnungslogik wie `trice insert`. Die zugeordneten IDs werden jedoch nicht in die Trice-Aufrufe der Userquellen geschrieben. Stattdessen erzeugt `trice bind` pro Source- oder Headerdatei einen temporären Sidecar-Header mit Präprozessordefinitionen.

Der Usercode bleibt beispielsweise:

```c
trice("msg:Hello trice bind world\n");
```

Die dauerhaften Informationen liegen in:

- `til.json`,
- `li.json`,
- der einmalig in die jeweilige Userdatei eingefügten Sidecar-Include-Zeile mit stabilem File Key.

Die Sidecar-Header sind reproduzierbare Buildartefakte. Der Compiler übersetzt unmittelbar die Userquellen und erhält die zugehörigen IDs über diese Header als Compile-Time-Konstanten.

Der normale Bind-Workflow lautet nach der einmaligen Migration:

```text
trice bind
Build
```

`trice clean` wird in einem stabilen Bind-Projekt nicht mehr regelmäßig benötigt.

### 1.1 Ergebnis eines Bind-Laufs

Für eine Datei `module.c` kann die versionierte Include-Zeile beispielsweise lauten:

```c
#include "trice_module_c_K73A915E9C4021B8.h" // trice-bind
```

Der zugehörige generierte Sidecar unter `./build/triceIDs` enthält sinngemäß:

```c
// Generated by trice bind. Do not edit.

#undef TRICE_SOURCE_KIND
#define TRICE_SOURCE_KIND TRICE_SOURCE_BOUND

#undef TRICE_FILE_KEY
#define TRICE_FILE_KEY K73A915E9C4021B8

#define TRICE_ID_K73A915E9C4021B8_L9      12345u
#define TRICE_BIND_HAS_TID_K73A915E9C4021B8_L9 0
#define TRICE_BIND_TID_K73A915E9C4021B8_L9     iD(12345u) // trice("msg:Hello trice bind world\n")
```

Die exakten internen Makronamen sind nicht normativ. Normativ sind:

- ein stabiler File Key,
- eine lesbare numerische ID-Definition,
- ein eindeutiger Site-Deskriptor für die Sourcezeile,
- die vollständige Stamp-Form `iD`, `id`, `Id` oder `ID`,
- die Information, ob die Userstelle ID-frei war oder einen Null-Platzhalter enthielt.

### 1.2 Grundmechanik der Präprozessorauflösung

Die Target-Library bildet den aktiven File Key und `__LINE__` auf den zugehörigen Site-Deskriptor ab:

```c
#define TRICE_BIND_CAT_I(prefix, key, line) prefix##key##_L##line
#define TRICE_BIND_CAT(prefix, key, line)   TRICE_BIND_CAT_I(prefix, key, line)

#define TRICE_BIND_ID_HERE() \
    TRICE_BIND_CAT(TRICE_ID_, TRICE_FILE_KEY, __LINE__)

#define TRICE_BIND_TID_HERE() \
    TRICE_BIND_CAT(TRICE_BIND_TID_, TRICE_FILE_KEY, __LINE__)
```

An Sourcezeile 9 expandiert:

```text
TRICE_BIND_TID_HERE()
→ TRICE_BIND_CAT(TRICE_BIND_TID_, K73A915E9C4021B8, 9)
→ TRICE_BIND_TID_K73A915E9C4021B8_L9
→ iD(12345u)
```

Der bestehende interne Trice-Pfad erhält dadurch denselben fachlichen TID-Ausdruck, den `trice insert` in den Source geschrieben hätte. Es gibt keinen Runtime-Lookup und keine Mappingtabelle im Target.

Die vollständige Grundmechanik einschließlich ID-freier Aufrufe und Null-Platzhalter ist in [Anhang C](#anhang-c-target-makrodispatch-und-präprozessorauflösung) beschrieben.

In diesem Dokument bedeuten:

## 3. Kompatibilität und Target-Zustände

### 3.1 Keine beabsichtigten Breaking Changes

Das MVP ist als additive Erweiterung spezifiziert.

Insbesondere gilt:

- `trice insert` bleibt verfügbar.
- `trice clean` bleibt verfügbar.
- Bestehende CLI-Aufrufe behalten ihre Bedeutung.
- Bestehende Projekte mit nicht definiertem `TRICE_CLEAN`, `TRICE_CLEAN 0` oder `TRICE_CLEAN 1` bleiben kompatibel.
- Das Schema von `til.json` und `li.json` wird nicht geändert.
- Das Trice-Drahtformat wird nicht geändert.
- Eine einzige Trice-Library unter `./src` unterstützt Insert-, Bind- und Clean-Projekte.
- Es wird keine separate Bind-Library und keine projektspezifisch generierte Librarykopie benötigt.
- Ein neues öffentliches `TRICE_MODE` ist nicht vorgesehen.

Falls sich während der Implementierung eine Abweichung als unvermeidbar erweist, MUSS sie vor dem Merge ausdrücklich als Breaking Change dokumentiert, begründet und mit einer Migrationsanleitung versehen werden. Nach aktuellem Stand ist dies nicht erforderlich.

### 3.2 Implizite Auswahl zwischen Inserted und Bind

Die Target-Library unterscheidet den Inserted- und Bind-Zustand anhand des lokal aktiven Sidecars.

Ohne Sidecar gilt intern standardmäßig die bisherige Inserted-Semantik:

```text
kein Sidecar aktiv
→ öffentliche Trice-Makros erwarten die bisherige explizite TID als erstes Argument
```

Ein Sidecar setzt vor den Trice-Stellen seiner physischen Datei einen internen Dispatch-Wert und den File Key:

```c
#undef TRICE_SOURCE_KIND
#define TRICE_SOURCE_KIND TRICE_SOURCE_BOUND

#undef TRICE_FILE_KEY
#define TRICE_FILE_KEY K73A915E9C4021B8
```

Dadurch gilt an den nachfolgenden Aufrufstellen:

```text
Sidecar aktiv
→ öffentliche Trice-Makros verwenden die Site-Deskriptoren aus dem Sidecar
```

`TRICE_SOURCE_KIND` ist ein interner Dispatch-Mechanismus der Library und der generierten Sidecars. Er ist keine neue Useroption in `triceConfig.h`.

Die Makroersetzung des öffentlichen Trice-Makros wird erst an der tatsächlichen Aufrufstelle expandiert. Deshalb kann ein nach `trice.h` inkludierter Sidecar den dort definierten Makropfad lokal auswählen.

### 3.3 Rolle von `TRICE_CLEAN`

`TRICE_CLEAN` bleibt optional und behält seine bisherige Funktion.

Bei:

```c
#define TRICE_CLEAN 1
```

verwendet die Library den bisherigen Clean-/Off-Pfad. Vorhandene Sidecars sind dann für die Codegenerierung unerheblich; die Trice-Aufrufe erzeugen keinen normalen Logging-Code.

Ist `TRICE_CLEAN` nicht definiert oder gleich `0`, gilt:

- eigener Sidecar aktiv → Bind-Semantik,
- kein eigener Sidecar aktiv → bisherige Inserted-Semantik.

Die vollständige Zustandsentscheidung lautet damit:

```text
TRICE_CLEAN == 1
    → Clean/Off

TRICE_CLEAN != 1 und Sidecar aktiv
    → Bind

TRICE_CLEAN != 1 und kein Sidecar aktiv
    → Inserted
```

Ein neues `TRICE_MODE` würde diese bereits vorhandenen Informationen duplizieren und wird deshalb nicht eingeführt.

### 3.4 Verhalten der Werkzeuge gegenüber `TRICE_CLEAN`

Ist eine Definition von `TRICE_CLEAN` in `triceConfig.h` vorhanden, gilt:

- `trice insert` setzt sie wie bisher auf `0`.
- `trice clean` setzt sie wie bisher auf `1`.
- `trice bind` setzt sie auf `0`, damit der Bind-Pfad aktiv ist.

Fehlt die Definition, fügt keines dieser Werkzeuge allein für den Bind-Workflow eine neue `TRICE_CLEAN`-Zeile ein.

`trice bind` entfernt eine bestehende `TRICE_CLEAN`-Definition nicht. Die Definition bleibt eine zulässige Useroption.

### 3.5 Projektweite Vorbedingung: keine expliziten IDs größer null

Im Bind-Modus sind explizite IDs größer null projektweit in allen vom ID-Parser verwalteten Bereichen verboten:

```c
TRICE(ID(7), "msg:hi\n"); // Fehler bei trice bind
trice(iD(8), "msg:hi\n"); // Fehler bei trice bind
```

Erlaubt bleiben Null-Platzhalter, weil sie die Stamp-Semantik festlegen:

```c
TRICE(id(0), "msg:hi\n");
TRICE(Id(0), "msg:hi\n");
TRICE(ID(0), "msg:hi\n");
```

Das Verbot gilt über alle gescannten Projektdateien hinweg und nicht nur innerhalb einzelner Dateien. Bereiche zwischen `TRICE_INSERT_OFF` und `TRICE_INSERT_ON` werden entsprechend der bestehenden Parsersemantik nicht verwaltet und sind davon ausgenommen.

Findet `trice bind` eine explizite ID größer null, sammelt es die Diagnose und beendet den Lauf mit Fehlerstatus. Die Meldung SOLL auf die Migration hinweisen:

```text
error: src/module.c:42: explicit ID 7 is not allowed in bind mode; run trice clean first
```

Diese Regel vereinfacht die Target-Makroschicht, verhindert eine Mischung unterschiedlicher ID-Quellen und stellt einen eindeutigen Projektzustand her.

## 4. Umfang des MVP

### 4.1 Gemeinsame Parser- und ID-Logik mit `trice insert`

`trice bind` MUSS denselben Parser und dieselbe Makroerkennung wie `trice insert` verwenden. Eine unabhängig nachimplementierte, nur ähnliche Erkennung ist nicht ausreichend, weil sie langfristig von `insert` abweichen würde.

Falls die aktuelle Implementierung keine direkte Wiederverwendung erlaubt, MUSS die gemeinsame Erkennungs- und Zuordnungslogik extrahiert beziehungsweise parametrisiert werden, ohne das Verhalten von `trice insert` zu ändern.

Wiederzuverwenden sind insbesondere:

- Erkennung der User-Level-Trice-Makros,
- Alias- und Simple-Alias-Behandlung,
- ID-Wrapper-Erkennung,
- Maskierung ausgeschlossener Bereiche,
- Typ- und Formatstring-Ermittlung,
- vorhandene Syntax- und Konsistenzprüfungen,
- Wiederverwendung bestehender IDs,
- Vergabe neuer IDs,
- ID-Range und Vergabemethode,
- Aktualisierung von `til.json` und `li.json`,
- `-defaultStampSize`.

### 4.2 Unterstützte User-Level-Makros

Das MVP MUSS dieselben eingebauten User-Level-Trice-Makros binden, die der bestehende `trice insert`-Parser unterstützt und für die ein Target-Makro vorhanden ist.

Dazu gehören insbesondere:

- die generischen Case-Familien `trice`, `Trice`, `TRice` und `TRICE`,
- die Bitbreitenfamilien 8, 16, 32 und bei aktivierter Unterstützung 64,
- variadische und explizit aritätscodierte Formen wie `Trice16(...)`, `TRice16_2(...)` und `TRICE8_3(...)`,
- Formen wie `trice0`, `trice_0` und ihre unterstützten Case-Varianten,
- String-, Count-, Buffer-, Float-, RPC-/ABC- und Assertion-Familien,
- User-Level-Sondermakros wie `triceAssertOrReturnValue`, soweit sie heute vom Insert-Parser verarbeitet werden,
- die von `trice insert` unterstützten `-alias`- und `-salias`-Namen.

Die Vollständigkeitsreferenz besteht aus:

1. der gemeinsamen Parserlogik,
2. den User-Level-Makros der Target-Library,
3. `_test/testdata/triceCheck.c`.

`_test/testdata/triceCheck.c` SOLL so ergänzt werden, dass es alle positiv unterstützten User-Level-Formen repräsentiert. Nicht unterstützte Konstruktionen gehören in separate Negativtests.

Neue User-Level-Trice-Makros gelten künftig nur dann als vollständig integriert, wenn ihr Insert- und Bind-Verhalten festgelegt und getestet ist.

### 4.3 Zwei bindbare ID-Zustände

Im Bind-MVP werden zwei ID-Zustände unterstützt.

#### A. ID-freier Aufruf

```c
trice("msg:hello\n");
TRice16_2("msg:x=%d y=%d\n", x, y);
TRICE8_3("msg:%d %d %d\n", a, b, c);
```

`trice bind` bestimmt die stabile ID. Der Sidecar enthält den vollständigen TID-Ausdruck für die Stelle.

Für Makrofamilien mit mindestens einem Kleinbuchstaben wird `iD(...)` verwendet. Die Targetstamp-Bitbreite ergibt sich weiterhin aus der vorhandenen Case-Semantik der ersten Buchstaben.

Für ausschließlich großgeschriebene Makros bestimmt `-defaultStampSize` die Wrapperform:

- `0` → `id(...)`,
- `16` → `Id(...)`,
- `32` → `ID(...)`.

#### B. Null-Platzhalter

```c
TRICE8_3(id(0), "msg:%d %d %d\n", a, b, c);
TRICE8_3(Id(0), "msg:%d %d %d\n", a, b, c);
TRICE8_3(ID(0), "msg:%d %d %d\n", a, b, c);
```

Die Wrapperform `id`, `Id` beziehungsweise `ID` MUSS erhalten bleiben, weil sie unterschiedliche Targetstamp-Aktionen auslöst. Der Sidecar liefert denselben Wrapper mit der stabilen ID statt der Null.

Ein expliziter Null-Platzhalter hat Vorrang vor `-defaultStampSize`.

#### C. Explizite ID größer null

Explizite IDs größer null werden vom Parser erkannt und mit der bestehenden Insert-Semantik validiert, führen im Bind-Lauf jedoch immer zu einer Projektfehlerdiagnose gemäß Abschnitt 3.5.

Sie erhalten keinen Bind-Sidecar-Eintrag.

### 4.4 Stamp-Semantik

Die bestehende Insert-Semantik bleibt maßgeblich. `trice bind` führt keine neue Case-Codierung ein.

Insbesondere:

- lower- und mixed-case Trice-Familien verwenden `iD(...)`,
- ausschließlich großgeschriebene `TRICE...`-Formen verwenden `id(...)`, `Id(...)` oder `ID(...)`,
- ein vorhandener Null-Platzhalter behält exakt seine Wrapperform,
- ein ID-freies Uppercase-Makro verwendet den mit `-defaultStampSize` gewählten Default,
- nichtkanonische, aber von `insert` akzeptierte Schreibweisen folgen derselben Entscheidung wie `trice insert`.

Neue schwer unterscheidbare Case-Varianten wie `trRICE` oder `TrICE` zur zusätzlichen Stamp-Codierung sind nicht Bestandteil des MVP.

### 4.5 Aliase

`trice bind` MUSS `-alias` und `-salias` im exakt gleichen Umfang wie `trice insert` unterstützen.

Es wird keine über `insert` hinausgehende neue Aliassemantik eingeführt.

Ein transparenter Alias auf eine bestehende Trice-Familie wird durch die gemeinsame Parserlogik erfasst. Eine projektspezifische Makrodefinition, die selbst einen Trice-Aufruf enthält oder Argumente transformiert, ist kein bloßer Alias und fällt unter die Einschränkung „Trice-Aufruf in Makrodefinition“ aus [Anhang A.2](#a2-trice-aufruf-in-einer-präprozessormakrodefinition).

Die Tests und Dokumentation sollen mindestens je ein funktionierendes Beispiel für `-alias` und `-salias` enthalten.

### 4.6 Parser-Ausschlussmarker

`trice bind` MUSS die bestehenden Marker exakt wie `trice insert` berücksichtigen:

```c
// TRICE_INSERT_OFF
...
// TRICE_INSERT_ON
```

Der vorhandene Maskierungsmechanismus soll wiederverwendet werden. Ausgeschlossene Bereiche:

- erhalten keine ID-Zuordnung,
- erzeugen keine Sidecar-Stelle,
- werden bei bind-spezifischen Syntaxprüfungen ignoriert,
- dürfen die Byteoffsets und Zeilennummern des übrigen Dateiinhalts nicht verändern.

Eine spätere neutralere Synonymbezeichnung wie `TRICE_ID_OFF` und `TRICE_ID_ON` kann separat eingeführt werden. Sie ist nicht Bestandteil des MVP und ersetzt die bestehenden Marker nicht.

### 4.7 Unterstützte Sourcekontexte

Das MVP unterstützt direkte User-Level-Trice-Aufrufe in:

- C- und C++-Sourcedateien,
- Headerdateien,
- normalen Funktionen,
- `inline`- und `static inline`-Funktionen.

Ein direkter Aufruf in einem Header wird der physischen Headerdatei und deren File Key zugeordnet. Wird derselbe Header in mehreren Translation Units verarbeitet, verwenden alle Instanzen dieser textuellen Source-Logstelle dieselbe stabile Trice-ID.

Die textuelle Definitionsstelle ist maßgeblich, nicht die spätere Inlining- oder Codegenerierungsentscheidung des Compilers.

### 4.8 Nicht unterstützte Konstruktionen

Das MVP unterstützt zunächst nicht:

- mehrere bindbare Trice-Stellen in derselben physischen Sourcezeile,
- Trice-Aufrufe innerhalb gewöhnlicher Präprozessormakrodefinitionen,
- durch Präprozessorlogik zusammengesetzte oder veränderte Formatstrings, soweit diese bereits außerhalb des Insert-Modells liegen,
- nicht transparente Custom-Wrapper außerhalb der von `insert` unterstützten Aliassemantik,
- explizite IDs größer null in den von `trice bind` verwalteten Projektbereichen.

Diese Fälle werden nicht stillschweigend durch einen Teil-`insert`-Fallback instrumentiert. Sie führen zu gesammelten Diagnosen.

Details, Anwendungsfälle und spätere Lösungsoptionen stehen in [Anhang A](#anhang-a-nicht-unterstützte-konstruktionen-im-mvp).

## 5. File Key, Sidecar und persistente Dateizuordnung

### 5.1 Dateilokaler Include ist erforderlich

Jede physische Datei mit bindbaren Trice-Stellen enthält einen zugehörigen Sidecar-Include:

```c
#include "trice_module_c_K73A915E9C4021B8.h" // trice-bind
```

Der Include erfüllt drei Aufgaben:

1. Er speichert den stabilen File Key in der versionierten Userdatei.
2. Er aktiviert lokal den Bind-Dispatch.
3. Er setzt vor den Trice-Stellen der physischen Datei den zugehörigen `TRICE_FILE_KEY`.

Eine zentrale Einbindung aller Sidecars in `triceConfig.h` ersetzt diese lokale Auswahl nicht. Der Standardpräprozessor kann aus dem Stringliteral `__FILE__` keinen passenden dynamischen Makronamen bilden. In einer Translation Unit können außerdem nacheinander Sidecars mehrerer Header und der `.c`-Datei verarbeitet werden. Der jeweils lokale Include stellt deshalb den richtigen Dateikontext her.

### 5.2 File Key

Der File Key ist ein einmalig erzeugter zufälliger 64-Bit-Wert, beispielsweise:

```text
K73A915E9C4021B8
```

Eigenschaften:

- Präfix `K` zur Kennzeichnung als Key,
- 16 großgeschriebene Hexadezimalziffern,
- Erzeugung mit der Go-Standardbibliothek `crypto/rand`,
- Speicherung im Sidecar-Include-Namen der Userdatei,
- Wiederverwendung bei späteren Läufen,
- keine Neuberechnung bei Dateiinhalt-, Pfad- oder Namensänderungen,
- keine Übertragung zum Target,
- kein Speicherverbrauch im Target,
- keine Änderung des `til.json`- oder `li.json`-Schemas.

Beispiel:

```go
func newFileKey() (string, error) {
    var b [8]byte
    if _, err := rand.Read(b[:]); err != nil {
        return "", err
    }
    return "K" + strings.ToUpper(hex.EncodeToString(b[:])), nil
}
```

`trice bind` MUSS projektweit prüfen, dass derselbe Key nicht von unterschiedlichen physischen Besitzerdateien beansprucht wird.

Dabei ist zu unterscheiden:

- **Fehler:** Zwei unterschiedliche Projektdateien enthalten denselben eigenen Sidecar-Include beziehungsweise File Key, typischerweise nach dem Kopieren einer Datei einschließlich Include-Zeile.
- **Zulässig:** Derselbe Header und sein Sidecar werden über normale Includes in mehreren Translation Units verarbeitet.

Bei einer Neukollision während der Key-Erzeugung wird ein neuer Wert erzeugt.

### 5.3 Sidecar-Dateiname und Ausgabeordner

Das Namensschema lautet:

```text
trice_<normalisierter-Basisname>_<FileKey>.h
```

Beispiel:

```text
module.c
→ trice_module_c_K73A915E9C4021B8.h
```

Der Basisname einschließlich Source-Extension verbessert die Lesbarkeit. Zeichen außerhalb `[A-Za-z0-9_]` werden durch `_` ersetzt. Die Eindeutigkeit liefert der File Key.

Alle Sidecars liegen standardmäßig in einem flachen Ordner:

```text
./build/triceIDs
```

Der Compiler benötigt dafür einen zusätzlichen Include-Pfad.

Der normalisierte `-bindDir`-Pfad MUSS automatisch vom Source-Scan ausgeschlossen werden. Dadurch werden eigene generierte Artefakte nicht rekursiv als Projektquellen analysiert. Dies gilt auch dann, wenn der User `-src .` verwendet und den Buildordner nicht ausdrücklich mit `-exclude` angegeben hat.

Ein defensiver Parser-Ausschlusskommentar im Sidecar ist zulässig, ersetzt diesen Pfadausschluss jedoch nicht.

### 5.4 Erkennung eines vorhandenen Sidecar-Includes

Die Identität des Includes ergibt sich aus dem Sidecar-Dateinamen und dem enthaltenen File Key. Der Kommentar `// trice-bind` ist nicht Teil der Identität.

Folgende Formen müssen sinngemäß erkennbar sein:

```c
#include "trice_module_c_K73A915E9C4021B8.h"
#include "trice_module_c_K73A915E9C4021B8.h" // trice-bind
# include "trice_module_c_K73A915E9C4021B8.h"
```

Wird nur der Kommentar entfernt, bleibt der Include gültig. `trice bind` fügt keinen zweiten Include ein und gibt dafür keine Warnung aus.

Der Kommentar wird bei automatisch neu eingefügten Includes weiterhin erzeugt, weil er die menschliche Lesbarkeit und Suche verbessert.

Wird die gesamte Include-Zeile entfernt, ist der File Key nicht mehr dauerhaft in der Userdatei gespeichert. Beim nächsten Bind-Lauf wird ein neuer Key erzeugt. Die stabilen Trice-IDs werden weiterhin über `til.json`, `li.json`, Typ, Formatstring und Location-Kontext wiederverwendet, soweit die bestehende Insert-Logik die Stellen eindeutig erkennt.

### 5.5 Sidecar-Inhalt

Ein Sidecar enthält mindestens:

```c
// Generated by trice bind. Do not edit.

#undef TRICE_SOURCE_KIND
#define TRICE_SOURCE_KIND TRICE_SOURCE_BOUND

#undef TRICE_FILE_KEY
#define TRICE_FILE_KEY K73A915E9C4021B8

#define TRICE_ID_K73A915E9C4021B8_L9 12345u
#define TRICE_BIND_HAS_TID_K73A915E9C4021B8_L9 0
#define TRICE_BIND_TID_K73A915E9C4021B8_L9 iD(12345u) // trice("msg:Hello trice bind world\n")
```

Für einen Null-Platzhalter kann der Eintrag beispielsweise lauten:

```c
#define TRICE_ID_K73A915E9C4021B8_L17 12346u
#define TRICE_BIND_HAS_TID_K73A915E9C4021B8_L17 1
#define TRICE_BIND_TID_K73A915E9C4021B8_L17 ID(12346u) // TRICE(ID(0), "msg:value=%d\n", value)
```

Normativ ist:

- Die numerische ID ist als einzelne lesbare Definition vorhanden.
- Der vollständige TID-Ausdruck ist eindeutig verfügbar.
- Für den Target-Dispatch ist erkennbar, ob das erste Userargument ein zu verwerfender Null-Platzhalter ist.
- Die Kommentare nennen den normalisierten Trice-Aufruf beziehungsweise mindestens den Formatstring.
- Die Reihenfolge ist nach Sourcezeile deterministisch.
- Eine Datei wird nur ersetzt, wenn sich ihr Inhalt tatsächlich ändert.

Mehrzeilige Trice-Aufrufe werden im Kommentar einzeilig dargestellt. Der Kommentar enthält die erste relevante Sourcezeile und endet bei weiteren Zeilen oder bei einer Längenbegrenzung mit `...`. Zeilenumbrüche und Steuerzeichen werden sicher normalisiert. Ein Backslash darf niemals das letzte Zeichen der generierten Kommentarzeile sein.

### 5.6 Kein klassischer Include-Guard

Der Sidecar erhält keinen klassischen Include-Guard.

Eine erneute Einbindung desselben Sidecars kann erforderlich sein, um nach einem zwischenzeitlich inkludierten Header den File Key der aktuellen Datei wiederherzustellen. Ein klassischer Include-Guard würde diese erneute Aktivierung verhindern.

Mehrere identische eigene Sidecar-Includes in derselben physischen Datei sind zulässig, werden aber von `trice bind` als Warnung gemeldet. Sie dürfen nicht mit der fehlerhaften Situation verwechselt werden, dass unterschiedliche Besitzerdateien denselben File Key beanspruchen.

### 5.7 Datei ohne aktuelle Trice-Stelle

Existiert eine gültige Sidecar-Include-Zeile, obwohl die Datei aktuell keine bindbare Trice-Stelle mehr enthält, bleibt die Include-Zeile erhalten. Der Sidecar KANN nur den Dispatch und den File Key setzen.

Dadurch bleibt die Dateiidentität stabil. Eine strengere Hygieneprüfung ist Aufgabe eines späteren `-check`-Modus.

## 6. Verwaltung der Sidecar-Includes

### 6.1 Erwartete Include-Position

Der Sidecar einer physischen Datei muss aktiv sein, wenn deren direkte Trice-Aufrufe expandiert werden.

Für eine typische `.c`-Datei gilt:

```c
#include "trice.h"
#include "module.h"
#include "driver.h"

#include "trice_module_c_K73A915E9C4021B8.h" // trice-bind

void moduleInit(void)
{
    trice("msg:module initialized\n");
}
```

Header mit eigenen direkten Trice-Aufrufen enthalten entsprechend ihren eigenen Sidecar innerhalb des Include-Guards und vor der ersten eigenen Trice-Stelle.

Die Sidecars eingebundener Header können den aktiven File Key umschalten. Deshalb muss eine `.c`-Datei nach ihren normalen Header-Includes ihren eigenen Sidecar aktivieren.

### 6.2 Bereits vorhandener Include

Ist ein passender Include vorhanden, belässt `trice bind` ihn grundsätzlich an seiner Position.

Version 1 prüft mindestens:

- Der File Key und der Sidecar-Name sind syntaktisch gültig.
- Derselbe Besitzerfile beansprucht nicht widersprüchlich verschiedene Keys.
- Der Include steht vor der ersten bindbaren Trice-Stelle, für die er gelten soll.
- Vor einer bindbaren Trice-Stelle wurde der File Key nicht offensichtlich durch einen späteren fremden Include ungültig gemacht, ohne dass der eigene Sidecar erneut aktiviert wurde.

Eine vollständige semantische Auswertung beliebiger C/C++-Präprozessorzweige ist nicht Teil des MVP.

### 6.3 Automatisches Einfügen

Fehlt ein Sidecar-Include, fügt `trice bind` ihn standardmäßig automatisch ein. Eine separate Option `-insertIncludes` ist für das MVP nicht vorgesehen.

Die einfache Heuristik lautet:

1. Alle textuell erkennbaren `#include`-Direktiven vor der ersten bindbaren Trice-Stelle bestimmen.
2. Den Sidecar nach der letzten solchen Include-Direktive einfügen.
3. Bei Headerdateien den Include innerhalb eines eindeutig erkennbaren äußeren Include-Guards platzieren.
4. Die Zeile mit `// trice-bind` markieren.

Kann keine sichere einfache Position bestimmt werden, verändert `trice bind` die Datei nicht und meldet eine Diagnose mit der exakt benötigten Include-Zeile.

Mindestens folgende Situationen gelten für die automatische Einfügung als nicht sicher:

- Eine bindbare Trice-Stelle steht vor einer späteren `#include`-Direktive.
- Zwischen bindbaren Trice-Stellen stehen weitere Includes.
- Die wahrscheinlich letzte Include-Direktive liegt innerhalb eines Präprozessorzweigs, dessen Ende vor der Trice-Stelle nicht eindeutig strukturell ermittelt werden kann.
- Ein Include wird über ein Makro angegeben, beispielsweise `#include HEADER_NAME`.
- Ein Header besitzt keinen für die einfache Heuristik eindeutig erkennbaren äußeren Include-Guard und die Einfügeposition wäre dadurch mehrdeutig.

Die Diagnose zeigt Datei, Position und den einzufügenden Text. Der User kann die Include-Zeile anschließend manuell an eine geeignete Stelle setzen. Ein späterer Bind-Lauf erkennt sie auch ohne den Kommentar wieder.

Komplexere Branch-, Guard- und Hygieneanalysen können später im `-check`-Modus ergänzt werden.

### 6.4 Textuelle Zustandsprüfung innerhalb einer Datei

Für die bindbaren direkten Trice-Stellen wird der Dateitext in Source-Reihenfolge betrachtet:

- Ein eigener Sidecar-Include aktiviert den eigenen File Key.
- Ein anderer Include kann den aktiven File Key potenziell verändern.
- Vor jeder bindbaren Trice-Stelle muss der eigene File Key textuell wieder aktiviert sein.

Dadurch kann ein User bei ungewöhnlicher Include-Struktur denselben eigenen Sidecar bei Bedarf erneut einbinden:

```c
#include "trice_module_c_K73A915E9C4021B8.h"
trice("msg:first\n");

#include "late_header.h"
#include "trice_module_c_K73A915E9C4021B8.h"
trice("msg:second\n");
```

Die mehrfache identische Einbindung wird gewarnt, bleibt aber funktional zulässig.

### 6.5 Zeilennummer nach Include-Einfügung

Die geplante Include-Zeile wird zunächst in den In-Memory-Dateiinhalt eingefügt. Parser, virtueller Insert-Pass und Sidecar-Rendering arbeiten anschließend auf diesem finalen Inhalt.

Dadurch stimmen die im Sidecar verwendeten `L<n>`-Werte unmittelbar mit den Sourcezeilen überein, die der Compiler verarbeitet.

Wird eine Datei später so editiert, dass sich die Zeile einer Trice-Stelle verschiebt, muss `trice bind` erneut laufen. Andernfalls referenziert `__LINE__` einen nicht vorhandenen Site-Makronamen und der Build soll mit einem Compilerfehler abbrechen, statt stillschweigend eine falsche ID zu verwenden.

### 6.6 Dry Run und Verbose-Ausgabe

`-dry-run` bleibt als vorhandene Insert-Option verfügbar.

Mit `-dry-run` werden:

- Source- und Listenänderungen berechnet,
- File Keys und Sidecar-Inhalte bestimmt,
- geplante Include-Zeilen und Diagnosen ausgegeben,
- aber keine Userdatei, JSON-Datei oder Sidecar-Datei geschrieben.

Im Verbose-Modus werden mindestens folgende Aktionen ausgegeben:

```text
bind: insert include: src/foo/module.c:17: #include "trice_module_c_K73A915E9C4021B8.h" // trice-bind
bind: write sidecar: build/triceIDs/trice_module_c_K73A915E9C4021B8.h
bind: reuse ID 12345: src/foo/module.c:42
```

Eine separate Option, die nur die Include-Einfügung abschaltet, ist für das MVP nicht vorgesehen. Der Dry Run deckt die sichere Vorschau ab, ohne einen zusätzlichen persistenten File-Key-Speicher zu benötigen.

## 7. Kommandozeilenschnittstelle

### 7.1 Subkommando

Das neue Subkommando lautet:

```sh
trice bind [Optionen]
```

Es verwendet dieselbe Cobra-/Flag-Infrastruktur wie die bestehenden ID-Kommandos und erscheint in `trice help` sowie `trice help -all`.

### 7.2 Verhältnis zu den Insert-Optionen

`trice bind` übernimmt grundsätzlich alle Optionen von `trice insert`, die Source-Suche, Parserverhalten, ID-Vergabe, Listenverwaltung und Validierung betreffen.

Die Dokumentation soll nicht alle gemeinsamen Optionen duplizieren, sondern nur die Abweichungen aufführen.

#### Identisch übernommen

Insbesondere:

- Source- und Suchpfade,
- Datei- und Verzeichnisausschlüsse,
- `-til` und `-li`,
- ID-Bereich und Vergabemethode,
- `-defaultStampSize`,
- `-alias` und `-salias`,
- Label-, Prüfsummen- und Konsistenzoptionen, soweit sie auf die ID-Datenbanken wirken,
- `-dry-run`,
- Verbosity- und Logoptionen.

#### Nicht oder nur bei definierter Wirkung übernommen

Optionen, die ausschließlich die textuelle Darstellung einer instrumentierten Userquelle, den Insert-Cache oder Insert-spezifisches Whitespace-Verhalten steuern, werden nicht automatisch für `bind` registriert. Sie werden nur übernommen, wenn ihre Wirkung im Bind-Ablauf eindeutig definiert ist.

#### Bind-spezifisch

```text
-bindDir string
    Ausgabeordner der Sidecar-Header.
    Default: ./build/triceIDs
```

Der Name kann an bestehende CLI-Namenskonventionen angepasst werden; die Semantik ist verbindlich.

### 7.3 Exitstatus und Diagnoseaggregation

- Keine Fehler: Exitstatus 0.
- Nur Warnungen: Exitstatus 0.
- Mindestens ein Fehler: Exitstatus ungleich 0.

Alle während der Analyse erkennbaren Diagnosen werden gesammelt. Ein Fehler in einer Datei beendet nicht die Analyse der übrigen Dateien vorzeitig.

Die Ausgabe wird nach normalisiertem Pfad, Zeile, Spalte und Schweregrad sortiert.

## 8. Verarbeitungsmodell

### 8.1 Phasen

Der MVP-Ablauf besteht aus folgenden Phasen:

1. Optionen validieren und Pfade normalisieren.
2. `til.json` und `li.json` mit den bestehenden Pre-Processing-Funktionen laden.
3. Kandidatendateien mit derselben Walk- und Ausschlusslogik wie `trice insert` bestimmen.
4. Den normalisierten `-bindDir` automatisch zur internen Ausschlussmenge hinzufügen.
5. Dateien parallel einlesen, Ausschlussbereiche maskieren und vorhandene Sidecar-Includes sowie File Keys erfassen.
6. Explizite IDs größer null und nicht unterstützte Konstruktionen projektweit diagnostizieren.
7. Fehlende Includes und neue File Keys planen.
8. Den finalen Sourcezustand einschließlich geplanter Includes im Speicher herstellen.
9. Die gemeinsame Insert-ID-Zuordnung auf diesem In-Memory-Inhalt ausführen, ohne den instrumentierten Inhalt in die Userdatei zurückzuschreiben.
10. Aus finalem und virtuell instrumentiertem Inhalt strukturierte Bind-Stellen erzeugen.
11. Alle Diagnosen und globalen Konflikte sammeln.
12. Bei fehlerfreier Analyse `til.json`, `li.json`, notwendige Include-Änderungen und Sidecars konsistent schreiben.

### 8.2 Wiederverwendung der Insert-Logik

Für die erste Implementierung SOLL die bestehende `trice insert`-Funktionalität möglichst weitgehend wiederverwendet werden.

Der wesentliche Unterschied lautet:

> Der durch die Insert-Logik erzeugte instrumentierte Sourceinhalt wird nicht als Userquelle gespeichert.

Er dient intern:

- als Referenz für die zugeordnete ID,
- als Referenz für die Stamp-Form,
- zur Ermittlung des ID-Zustands,
- zur Erzeugung der Sidecar-Site-Deskriptoren,
- zur Paritätsprüfung mit `trice insert` in Tests.

Die Funktion, welche den instrumentierten Inhalt tatsächlich in die Userdatei schreibt, darf vom Bind-Ablauf nicht aufgerufen werden.

Zusätzlicher Parse- und Speicheraufwand ist im MVP zulässig. Korrektheit, Parserparität und schnelle Implementierbarkeit haben Vorrang. Eine spätere direkte Site-Erfassung ist eine interne Optimierung.

### 8.3 Strukturierte Bind-Stellen

Für jede erkannte bindbare Stelle werden mindestens ermittelt:

```go
type bindIDState uint8

const (
    bindIDFree bindIDState = iota
    bindIDZeroPlaceholder
)

type bindStampForm uint8

const (
    bindStampID bindStampForm = iota // iD
    bindStamp0                        // id
    bindStamp16                       // Id
    bindStamp32                       // ID
)

type bindSite struct {
    Path       string
    FileKey    string
    Line       int
    Column     int
    MacroName  string
    AliasName  string
    Type       string
    Format     string
    ID         int
    IDState    bindIDState
    StampForm  bindStampForm
    SourceText string
}
```

Die genauen Go-Typnamen sind nicht normativ.

Explizite IDs größer null werden als Diagnosen erfasst, aber nicht als bindbare `bindSite` gerendert.

### 8.4 Parallelität

Die Dateiverarbeitung MUSS dieselbe Parallelitätsstrategie und soweit möglich dieselben Synchronisationsmechanismen wie `trice insert` verwenden.

Insbesondere darf `bind` große Projekte nicht als rein sequentielle Schleife verarbeiten.

Zulässig ist ein Modell mit:

- parallelem Einlesen und Analysieren pro Datei,
- gemeinsamem, durch vorhandene Mechanismen geschütztem ID-Allocator,
- paralleler Sidecar-Aufbereitung,
- abschließender konsistenter Commit-Phase.

Die Ausgabeordnung von Sidecars und Diagnosen wird unabhängig von der Goroutine-Reihenfolge deterministisch sortiert. Die ID-Vergabe folgt exakt der vorhandenen Insert-Semantik und darf durch `bind` keine neue Scheduling-Abhängigkeit erhalten.

### 8.5 Konsistentes Schreiben

Reguläre Ausgaben werden erst geschrieben, nachdem alle Dateien analysiert und globale Konflikte geprüft wurden.

Bei mindestens einem fatalen Fehler gilt:

- keine teilweise aktualisierte `til.json`,
- keine teilweise aktualisierte `li.json`,
- keine nur teilweise eingetragenen neuen Sidecar-Includes,
- keine Sidecar-Menge, die als vollständig gültig erscheinen könnte.

Dateien werden über temporäre Dateien und atomaren Ersatz geschrieben, soweit das Betriebssystem dies unterstützt. Ein bestehendes Artefakt wird nur ersetzt, wenn sich sein Inhalt tatsächlich ändert.

Verpflichtende diagnostische Schattenkopien unter `./TriceIDs` sind nicht Bestandteil des MVP. Parserparität wird in Tests mit temporären Testverzeichnissen und In-Memory-Vergleichen nachgewiesen.

## 9. Target-Makroarchitektur

### 9.1 Auswahl Clean/Off gegenüber aktiver Library

`trice.h` behält die bestehende übergeordnete Entscheidung anhand von `TRICE_CLEAN` beziehungsweise `TRICE_OFF` bei.

Schematisch:

```c
#if TRICE_OFF == 1 || TRICE_CLEAN == 1
#include "triceOff.h"
#else
#include "triceOn.h"
#endif
```

Die genaue bestehende Bedingung bleibt maßgeblich.

Der Bind-Dispatch existiert nur im aktiven `triceOn`-Pfad. Bei `TRICE_CLEAN == 1` sind vorhandene Sidecars für die Logging-Codegenerierung unerheblich.

### 9.2 Default Inserted, lokaler Bind-Dispatch

`triceOn.h` definiert intern einen Default für Dateien ohne Sidecar:

```c
#ifndef TRICE_SOURCE_KIND
#define TRICE_SOURCE_KIND TRICE_SOURCE_INSERTED
#endif
```

Ein Sidecar stellt lokal um:

```c
#undef TRICE_SOURCE_KIND
#define TRICE_SOURCE_KIND TRICE_SOURCE_BOUND
```

Die öffentlichen User-Level-Makros dispatchen bei ihrer Expansion auf den aktuellen Wert. Schematisch:

```c
#define TRICE_PUBLIC_SELECT_I(kind, family) \
    TRICE_PUBLIC_##kind##_##family

#define TRICE_PUBLIC_SELECT(kind, family) \
    TRICE_PUBLIC_SELECT_I(kind, family)

#define trice(...) \
    TRICE_PUBLIC_SELECT(TRICE_SOURCE_KIND, trice)(__VA_ARGS__)

#define TRICE(...) \
    TRICE_PUBLIC_SELECT(TRICE_SOURCE_KIND, TRICE)(__VA_ARGS__)
```

Die Namen sind nicht normativ. Entscheidend ist:

- ohne Sidecar wird die bisherige explizite-ID-Signatur verwendet,
- mit Sidecar wird die fehlende beziehungsweise null gesetzte TID über den Site-Deskriptor geliefert.

### 9.3 Inserted-Pfad

Der Inserted-Pfad verwendet die bestehenden Makroverträge unverändert.

Beispiel:

```c
trice(iD(12345), "msg:hello\n");
```

Schematisch:

```c
#define TRICE_PUBLIC_INSERTED_trice(tid, ...) \
    TRICE_EXISTING_TRICE_PATH(tid, __VA_ARGS__)
```

Es wird keine neue Bedeutung für ID-freie Aufrufe ohne Sidecar eingeführt. Ein bereinigter Source ohne Sidecar und ohne `TRICE_CLEAN == 1` ist weiterhin kein normaler aktiver Buildzustand.

### 9.4 Bind-Pfad und vom Generator gelieferter Site-Zustand

Der Generator kennt aus dem gemeinsamen Hostparser bereits, ob die Userstelle:

- ID-frei ist oder
- einen Null-Platzhalter enthält.

Der Sidecar stellt diese Information bereit:

```c
#define TRICE_BIND_HAS_TID_K73A915E9C4021B8_L9 0
#define TRICE_BIND_TID_K73A915E9C4021B8_L9 iD(12345u)

#define TRICE_BIND_HAS_TID_K73A915E9C4021B8_L12 1
#define TRICE_BIND_TID_K73A915E9C4021B8_L12 ID(12346u)
```

Die Target-Makros müssen daher nicht selbst durch Patternmatching feststellen, ob das erste Userargument `ID(0)` oder ein Formatstring ist.

Schematisch:

```c
#define TRICE_BIND_HAS_TID_HERE() \
    TRICE_BIND_CAT(TRICE_BIND_HAS_TID_, TRICE_FILE_KEY, __LINE__)

#define TRICE_BIND_TID_HERE() \
    TRICE_BIND_CAT(TRICE_BIND_TID_, TRICE_FILE_KEY, __LINE__)

#define TRICE_BIND_SELECT_I(hasTid, family, ...) \
    TRICE_BIND_##hasTid##_##family(__VA_ARGS__)

#define TRICE_BIND_SELECT(hasTid, family, ...) \
    TRICE_BIND_SELECT_I(hasTid, family, __VA_ARGS__)
```

Für die Familie `TRICE` beispielsweise:

```c
#define TRICE_PUBLIC_BOUND_TRICE(...) \
    TRICE_BIND_SELECT(TRICE_BIND_HAS_TID_HERE(), TRICE, __VA_ARGS__)

#define TRICE_BIND_0_TRICE(...) \
    TRICE_EXISTING_TRICE_PATH(TRICE_BIND_TID_HERE(), __VA_ARGS__)

#define TRICE_BIND_1_TRICE(_zeroPlaceholder, ...) \
    TRICE_EXISTING_TRICE_PATH(TRICE_BIND_TID_HERE(), __VA_ARGS__)
```

Damit sind diese vier Formen sauber behandelbar:

```c
TRICE("msg:hi\n");
TRICE(ID(0), "msg:hi\n");
TRICE("msg:hi %d\n", x);
TRICE(ID(0), "msg:hi %d\n", x);
```

Für ID-freie Stellen wird die TID vor allen Userargumenten ergänzt. Bei einem Null-Platzhalter wird das erste Userargument verworfen und durch den Sidecar-TID-Ausdruck ersetzt.

Explizite IDs größer null sind im Bind-Projekt verboten und müssen deshalb im Bind-Targetpfad nicht unterstützt werden.

### 9.5 Kein neues Target-Patternmatching für `ID(0)` erforderlich

Der bestehende Hostparser von `trice insert` unterscheidet bereits ID-freie, `id(0)`-, `Id(0)`- und `ID(0)`-Formen. `trice bind` übernimmt dieses Ergebnis in den Sidecar.

Die Target-Makros verwenden nur den generierten booleschen Site-Zustand und den vollständigen TID-Ausdruck. Dadurch entfällt eine komplizierte und fehleranfällige C-Präprozessorerkennung von `ID(0)` gegenüber einem Formatstring.

### 9.6 Makrofamilien

Die Bind-Erweiterung SOLL zentral und mechanisch implementiert werden.

| Gruppe | Beispiele | Hauptaufgabe |
|---|---|---|
| Generische lower-/mixed-case Familien | `trice`, `Trice`, `TRice` | Sidecar-TID einsetzen oder Null-Platzhalter verwerfen |
| Reine Uppercase-Familien | `TRICE`, `TRICE8_3`, `TRICE_0` | `-defaultStampSize` beziehungsweise vorhandene `id`/`Id`/`ID`-Form übernehmen |
| Breiten-/Arity-Familien | `TRice16_2`, `Trice32`, `trice64_4` | mechanisch auf den gemeinsamen Bind-Dispatch weiterleiten |
| String-/Buffer-/Count-Familien | `triceS`, `triceN`, `triceB`, `triceC` | vorhandene Argumentverträge beibehalten, nur TID-Zuführung ergänzen |
| Float-/RPC-/ABC-Familien | vorhandene Spezialformen | bestehende interne Pfade unverändert erreichen |
| Assertions und Control-Flow-Helfer | unter anderem `triceAssertOrReturnValue` | User-Level-Vertrag und intern erzeugte Trice-Stelle gemeinsam testen |
| `-alias`/`-salias` | insert-unterstützte Aliase | denselben kanonischen Bind-Pfad wie bei `insert` verwenden |

Vor der breiten Umsetzung SOLL ein Target-PoC mindestens folgende repräsentative Gruppen nachweisen:

1. `trice(...)`,
2. ein Uppercase-Makro wie `TRICE8_3(...)`,
3. eine Spezialform wie `triceS(...)` oder `triceC(...)`,
4. ein Assertion- beziehungsweise Control-Flow-Makro.

Falls die Umsetzung eine erhebliche vollständige Duplizierung der bestehenden Makrofamilien erfordern würde, muss die Makroarchitektur vor der Gesamtimplementierung erneut reviewed werden.

## 10. Migration, normaler Betrieb und Re-Migration

### 10.1 Migration von `trice insert` zu `trice bind`

Ausgangszustand eines Insert-Projekts:

```c
trice(iD(12345), "msg:hello\n");
```

Optional kann in `triceConfig.h` stehen:

```c
#define TRICE_CLEAN 0
```

#### Schritt 1: Quellen bereinigen

Vor dem ersten Bind-Lauf wird empfohlen:

```sh
trice clean [bisherige Optionen]
```

Dadurch werden explizite IDs aus den verwalteten Trice-Aufrufen entfernt:

```c
trice("msg:hello\n");
```

Falls `TRICE_CLEAN` vorhanden ist, setzt `trice clean` den Wert auf `1`.

Fehlt `TRICE_CLEAN`, wird keine Definition ergänzt.

#### Schritt 2: Binden

Danach:

```sh
trice bind [entsprechende Optionen]
```

`trice bind`:

- verifiziert projektweit, dass keine expliziten IDs größer null mehr vorhanden sind,
- erzeugt File Keys,
- fügt Sidecar-Includes ein,
- erzeugt Sidecars,
- aktualisiert `til.json` und `li.json` mit derselben fachlichen Semantik wie `insert`,
- setzt ein vorhandenes `TRICE_CLEAN 1` wieder auf `0`,
- fügt keine neue `TRICE_CLEAN`-Definition ein.

Danach ist der Projektzustand beispielsweise:

```c
#define TRICE_CLEAN 0 // nur falls bereits vorhanden
```

```c
#include "trice_module_c_K73A915E9C4021B8.h" // trice-bind

trice("msg:hello\n");
```

Der Build benötigt `./build/triceIDs` beziehungsweise den konfigurierten `-bindDir` als Include-Pfad.

### 10.2 Normaler Bind-Betrieb

Nach der Migration lautet der normale Ablauf dauerhaft:

```text
trice bind
Build
```

`TRICE_CLEAN` wird dabei nicht ständig als Workflowzustand umgeschaltet. Ist die Definition vorhanden, stellt `trice bind` lediglich sicher, dass sie `0` ist. Fehlt sie, ist keine Konfigurationsänderung erforderlich.

Die User-Trice-Aufrufe bleiben ID-frei. Änderungen an Sourcezeilen, Trice-Aufrufen oder ID-Datenbanken führen zu aktualisierten Sidecars.

### 10.3 Ergebnis von `trice bind`

Nach einem erfolgreichen Bind-Lauf gilt:

- User-Trice-Aufrufe enthalten keine numerischen IDs größer null.
- Null-Platzhalter können weiterhin im Source stehen.
- Sidecar-Includes sind in den Userdateien vorhanden und versioniert.
- Sidecar-Header liegen als nicht versionierte Buildartefakte vor.
- `til.json` und `li.json` enthalten die stabile Zuordnung.
- Ein vorhandenes `TRICE_CLEAN` steht auf `0`.
- Ohne `TRICE_CLEAN` ist keine zusätzliche Target-Konfiguration notwendig.
- Die Library erzeugt aktiven Trice-Code über den lokal gewählten Bind-Pfad.

### 10.4 `trice clean` nach `trice bind` mit vorhandenem `TRICE_CLEAN`

Ausgangszustand:

```c
#define TRICE_CLEAN 0
```

mit ID-freien Userquellen und vorhandenen Sidecars.

Wird nun ausgeführt:

```sh
trice clean
```

passiert:

- Die ID-freien Trice-Aufrufe bleiben unverändert.
- Null-Platzhalter bleiben entsprechend der bisherigen Clean-Semantik unverändert beziehungsweise werden nicht als eingesetzte ID größer null behandelt.
- Die Sidecar-Include-Zeilen bleiben erhalten.
- Die Sidecar-Dateien bleiben erhalten.
- `TRICE_CLEAN` wird auf `1` gesetzt.

Der resultierende Buildzustand ist:

```text
ID-freie Quellen + Sidecars + TRICE_CLEAN == 1
→ Clean/Off
```

Die Sidecars sind vorhanden, aber `trice.h` wählt den Clean-/Off-Pfad. Es wird kein normaler Trice-Logging-Code erzeugt.

Ein anschließendes:

```sh
trice bind
```

setzt ein vorhandenes `TRICE_CLEAN` wieder auf `0` und reaktiviert damit den Bind-Build. Source und Sidecar-Includes müssen dafür nicht erneut migriert werden.

### 10.5 `trice clean` nach `trice bind` ohne `TRICE_CLEAN`

Ist in `triceConfig.h` keine `TRICE_CLEAN`-Definition vorhanden, ist `trice clean` nach einem stabilen Bind-Lauf bezüglich des Buildzustands im Wesentlichen wirkungslos:

- Die User-Trice-Aufrufe sind bereits ID-frei und ändern sich nicht.
- Sidecar-Includes ändern sich nicht.
- Sidecar-Dateien werden nicht entfernt.
- Es wird keine `TRICE_CLEAN`-Definition neu angelegt.
- Die Sidecars wählen weiterhin lokal den Bind-Pfad.
- Ein anschließender Build bleibt ein aktiver Bind-Build.

`trice clean` ist damit kein Rückweg von Bind zu Insert und kein Mechanismus zum Entfernen einer Bind-Konfiguration.

Das Werkzeug KANN bei erkannten Sidecar-Includes eine informative Meldung ausgeben:

```text
project appears to use trice bind; no inserted source IDs were removed
```

Diese Meldung ist nicht Voraussetzung für die fachliche Funktion.

### 10.6 Unterschied Clean-Source ohne Sidecar und Bind-Source

Beide Sourceformen können ID-freie Trice-Aufrufe enthalten. Sie werden durch den Buildkontext unterschieden:

| Zustand | `TRICE_CLEAN` | eigener Sidecar | Wirkung |
|---|---:|---:|---|
| Inserted | nicht definiert oder `0` | nein | Trice-Makros erwarten explizite IDs im Source |
| Bind | nicht definiert oder `0` | ja | TID kommt aus dem Sidecar |
| Clean/Off | `1` | beliebig | bisheriger Clean-/Off-Pfad |
| nur bereinigt, nicht bindbar | nicht definiert oder `0` | nein | ID-freie Aufrufe erfüllen den aktiven Inserted-Vertrag nicht; kein normaler Buildzustand |

Dadurch ist kein globaler Bind-Modus erforderlich.

### 10.7 Manuelle Re-Migration von `bind` zu `insert`

Ein automatischer Rückweg ist für das MVP nicht erforderlich. Die manuelle Anleitung lautet:

1. Alle dateilokalen Sidecar-Includes entfernen oder auskommentieren.
2. Den Sidecar-Ausgabeordner bei Bedarf löschen.
3. `trice insert` mit den bisherigen Projektoptionen ausführen.
4. Den Bind-Include-Pfad aus dem Build entfernen, sofern er ausschließlich für Sidecars verwendet wurde.

Danach enthalten die Userquellen wieder explizite IDs:

```c
trice(iD(12345), "msg:hello\n");
```

Ist `TRICE_CLEAN` vorhanden, setzt `trice insert` es wie bisher auf `0`.

Die Sidecar-Includes müssen vor dem aktiven Inserted-Build entfernt werden, weil sie sonst weiterhin lokal den Bind-Dispatch auswählen würden.

`til.json` und `li.json` werden weiterverwendet; es ist keine neue ID-Datenbank erforderlich.

### 10.8 Zustands- und Werkzeugmatrix

| Ausgangszustand | Befehl | Source-IDs | Sidecar-Includes | Sidecars | `TRICE_CLEAN` | Resultierender Buildpfad |
|---|---|---|---|---|---|---|
| Inserted | `trice clean` | entfernt | unverändert/nicht vorhanden | unverändert | falls vorhanden: `1` | Clean/Off bei `1`, sonst nur bereinigter Source |
| Bereinigt | `trice bind` | bleiben frei | werden erzeugt | werden erzeugt | falls vorhanden: `0` | Bind |
| Bind | `trice bind` | bleiben frei | bleiben | werden aktualisiert | falls vorhanden: `0` | Bind |
| Bind | `trice clean`, `TRICE_CLEAN` vorhanden | bleiben frei | bleiben | bleiben | wird `1` | Clean/Off |
| Bind | `trice clean`, `TRICE_CLEAN` fehlt | bleiben frei | bleiben | bleiben | bleibt undefiniert | Bind bleibt aktiv |
| Bind | manuelle Re-Migration + `trice insert` | werden eingesetzt | vorher manuell entfernt | entbehrlich | falls vorhanden: `0` | Inserted |

## 11. Validierung und Diagnosen

### 11.1 Verbindliche MVP-Prüfungen

Version 1 MUSS alle Prüfungen enthalten, deren Auslassen falschen Targetcode oder eine falsche ID-Zuordnung ermöglichen könnte.

Mindestens:

- duplizierter File Key in unterschiedlichen Besitzerdateien,
- widersprüchlicher Sidecar-Name oder Key,
- explizite ID größer null in einem verwalteten Projektbereich,
- nicht auflösbare oder mehrfach belegte Bind-Stelle,
- mehrere bindbare Trice-Aufrufe auf derselben physischen Zeile,
- Trice-Aufruf in einer nicht unterstützten Makrodefinition,
- nicht von `insert` unterstützter Alias beziehungsweise Custom-Wrapper,
- Widerspruch zwischen ID, Typ, Formatstring, `til.json` oder `li.json`,
- ungültiger `-defaultStampSize`,
- fehlender oder für eine Stelle nicht aktiver eigener File Key,
- erzeugter Sidecar würde einen im Build nicht definierten Site-Namen liefern,
- alle heute von `trice insert` ausgeführten syntaktischen und semantischen Prüfungen einschließlich vorhandener Sonderbehandlungen für Makrofamilien wie `triceC`, Strings, Buffer, RPC/ABC und Assertions.

Wenn eine gewünschte Formatverb-, Parameterzahl- oder Spezialprüfung heute nicht in `insert` vorhanden ist, soll sie nicht nur für `bind` implementiert werden. Eine solche Verbesserung gehört in die gemeinsame Parser- beziehungsweise Validierungsschicht beider Befehle.

### 11.2 Warnungen

Warnungen sind insbesondere angemessen bei:

- mehrfacher identischer Einbindung desselben Sidecars in derselben Besitzerdatei,
- vorhandener Sidecar-Include-Zeile für eine Datei ohne aktuelle Trice-Stelle,
- ungewöhnlicher, aber eindeutig auswertbarer Include-Struktur,
- automatisch nicht sicher bestimmbarer Include-Position, sofern keine falsche Bindung erzeugt wurde,
- Artefakten, die bei einer optionalen Bereinigung nicht entfernt werden konnten.

Warnungen dürfen nicht zur stillen Akzeptanz einer nachweislich falschen Bindung führen.

### 11.3 Ausgabeformat

Diagnosen SOLLEN mindestens enthalten:

```text
<severity>: <path>:<line>:<column>: <message>
```

Beispiele:

```text
warning: src/module.c:18:1: sidecar is included more than once
error: include/log.h:27:5: Trice call inside macro definition is not supported by bind MVP
error: src/legacy.c:44:7: explicit ID 4711 is not allowed in bind mode; run trice clean first
```

Zusammenfassend werden Anzahl der analysierten Dateien, erzeugten beziehungsweise aktualisierten Sidecars, wiederverwendeten und neuen IDs, Warnungen und Fehler ausgegeben.

### 11.4 Späterer `-check`-Modus

Ein umfassender Hygiene-Modus ist nicht Voraussetzung der ersten Version.

Ein späteres:

```sh
trice bind -check
```

kann zusätzlich prüfen:

- Include eines leeren Sidecars,
- verwaiste Sidecars,
- Sidecars ohne zugehörige Projektdatei,
- unbenutzte File Keys,
- alte Definitionen im Sidecar,
- Abweichungen zwischen Source, Sidecar, `til.json` und `li.json`,
- fehlende Aktualisierung nach einer reinen Zeilenverschiebung,
- nicht mehr benötigte Include-Zeilen,
- komplexe bedingte Include-Strukturen.

Diese Prüfungen verändern den MVP-Bindemechanismus nicht.

## 12. Implementierungsumriss

### 12.1 Vorgeschlagene Verantwortlichkeiten

Die konkrete Dateiaufteilung darf an die bestehende Projektstruktur angepasst werden. Sinngemäß:

```text
cmd/ oder internal/...       Registrierung des Subkommandos und der Flags
internal/id/bindIDs.go       Orchestrierung des Bind-Ablaufs
internal/id/bindParse.go     Site-, Key- und Include-Analyse
internal/id/bindRender.go    Sidecar-Rendering
internal/id/bindTypes.go     interne Datenstrukturen und Diagnosen
src/trice*.h                 lokaler Inserted-/Bind-Dispatch der User-Level-Makros
```

Gemeinsame Insert-/Bind-Funktionalität darf nicht dupliziert werden. Geeignete vorhandene Funktionen werden extrahiert oder parametrisiert, sofern dies ohne Verhaltensänderung von `insert` möglich ist.

Die Bind-CLI-Parameter werden analog zu den Insert-Parametern in die vorhandene CLI- und Konfigurationsstruktur integriert. Es entsteht kein unabhängiges zweites Optionssystem.

### 12.2 Anpassung der Insert-Funktionen

Die bestehende Insert-Logik soll so parametrisiert werden, dass sie:

- wie bisher Userdateien instrumentieren kann,
- für `bind` denselben instrumentierten Inhalt nur im Speicher zurückliefert,
- optional strukturierte Informationen je erkannter beziehungsweise ersetzter Stelle an einen Collector meldet.

Für die erste Implementierung ist es zulässig, Site-Informationen aus dem Vergleich des finalen ID-freien und des virtuell instrumentierten Inhalts zu gewinnen. Ein Collector ist vorzuziehen, sobald er ohne Risiko für `insert` ergänzt werden kann.

### 12.3 Behandlung von `TRICE_CLEAN`

Der Bind-Orchestrator verwendet dieselbe vorhandene Erkennung der optionalen `TRICE_CLEAN`-Definition wie `insert` und `clean`.

Bei einem erfolgreichen realen Bind-Lauf:

- vorhandenes `TRICE_CLEAN 1` → auf `0` setzen,
- vorhandenes `TRICE_CLEAN 0` → unverändert lassen,
- keine Definition → nichts ergänzen.

Bei `-dry-run` wird nur die geplante Änderung ausgegeben.

### 12.4 Keine automatische Fallback-Instrumentierung

Version 1 führt bei einer nicht bindbaren Stelle keinen impliziten Teil-`insert` aus.

Beispiele:

```c
trice("msg:a\n"); trice("msg:b\n");
```

```c
#define LOG_ERROR(x) trice("msg:error=%d\n", x)
```

```c
#define PREFIX "msg:"
trice(PREFIX "value=%d\n", value);
```

Diese Stellen werden gesammelt gemeldet. Das bestehende `trice insert` bleibt als separater Workflow verfügbar.

### 12.5 Testdateisystem

Ein eigenes virtuelles Dateisystem ist nicht vorgeschrieben.

Go-Tests können mit `t.TempDir()` und realen temporären Dateien arbeiten. Dies bildet atomaren Ersatz, Dateizeitverhalten, Rename, Include-Einfügung und parallele Schreibzugriffe realistisch ab.

Falls das Repository bereits eine geeignete Dateisystemabstraktion besitzt, kann sie wiederverwendet werden.

## 15. Zukünftige Erweiterungen und Optimierungen

Dieser Abschnitt ist nicht Bestandteil des MVP-Verhaltens. Erweiterungen dürfen den bestehenden Sidecar-Mechanismus und die ID-Datenbanken nicht unnötig brechen.

### 15.1 Direkte Site-Erfassung ohne virtuellen Insert-Pass

Der gemeinsame Parser kann später die zugeordnete ID, Stamp-Form und Sourceposition direkt an einen Bind-Collector melden.

**Gewinn:** geringerer Speicher- und Laufzeitaufwand bei unverändertem Verhalten.

### 15.2 Analyse der aktiven Präprozessorkonfiguration

Ein optionaler Lauf des realen Präprozessors kann bestimmen, welche der textuell erfassten Logstellen in einer konkreten Buildkonfiguration aktiv sind.

**Erforderlich:** tatsächliche Compilerdefines, Include-Pfade und gegebenenfalls `compile_commands.json` oder eine gleichwertige Buildbeschreibung.

**Gewinn:** Bericht über die aktive Teilmenge. Die stabile ID-Vergabe bleibt sourcebasiert und erfasst weiterhin auch aktuell inaktive Stellen.

### 15.3 Post-Link-Image-Inventur

Eine optionale ELF- oder Link-Map-Analyse kann bestimmen, welche aktiven Logstellen nach Optimierung, LTO, Archivselektion und Section-Garbage-Collection im finalen Image enthalten sind.

**Gewinn:** exakte Buildinventur. Das Binding selbst bleibt unverändert.

### 15.4 Vorbereitete statische Libraries

Vorbereitete `.a`-Libraries können Metadaten und bindbare ID-Platzhalter enthalten. `trice bind` kann diese beim Produkt-Build in den stabilen ID-Raum einordnen.

**Erforderlich:** definiertes Library-Metadatenformat, bindbare Platzhalter und ein Link-Bindeartefakt.

**Gewinn:** stabile produktweite IDs für Libraries, deren Source beim Endprodukt nicht erneut gebunden wird.

### 15.5 Mehrere Trice-Aufrufe pro Zeile

Ein zusätzlicher Site-Index oder ein optionaler, nachweislich geeigneter `__COUNTER__`-Pfad kann mehrere Logstellen derselben physischen Zeile unterscheiden.

**Gewinn:** Unterstützung eines seltenen Codestils.

### 15.6 Trice-Aufrufe in Makrodefinitionen

Eine spätere Erweiterung kann eine Definitionsstellen-ID für Wrappermakros bereitstellen.

Denkbare Verfahren:

- expliziter bind-fähiger Wrapperadapter,
- selektiver und ausdrücklich aktivierter Insert-Kompatibilitätsmodus,
- präprozessorbasierte Erfassung mit festgelegter Definitionsstellen-Semantik.

**Gewinn:** Migration bestehender Wrappermakros wie `LOG_ERROR`.

Ein solcher Modus darf Sourcecode nicht stillschweigend verändern.

### 15.7 Neutralere Ausschlussmarker

Neue Marker wie:

```c
// TRICE_ID_OFF
// TRICE_ID_ON
```

können später als Synonyme zu `TRICE_INSERT_OFF` und `TRICE_INSERT_ON` eingeführt werden.

**Gewinn:** werkzeugneutralere Benennung ohne Breaking Change.

### 15.8 Umfassender Check-Modus

Der in Abschnitt 11.4 beschriebene Hygiene- und Konsistenzlauf kann unabhängig vom normalen Bind-Lauf ausgebaut werden.

## Anhang A: Nicht unterstützte Konstruktionen im MVP

### A.1 Mehrere Trice-Aufrufe in einer physischen Zeile

Beispiel:

```c
trice("msg:first\n"); trice("msg:second\n");
```

**Anwendungsfall:** stark komprimierter oder generierter Sourcecode.

**Problem:** Beide Stellen sehen denselben File Key und denselben Wert von `__LINE__`. Ein Site-Makroname kann sie deshalb nicht unterscheiden.

**Warum nicht im MVP:** Der übliche und lesbarere Stil verwendet getrennte Zeilen. Die Einschränkung ist leicht diagnostizierbar und vermeidet eine zusätzliche Toolchainannahme.

**Praktische Lösung im MVP:** Aufrufe auf getrennte Zeilen schreiben.

**Spätere Lösung:** zusätzlicher Auftretensindex oder optional `__COUNTER__`, sofern Generator- und Compilerlauf zuverlässig dieselbe Expansion liefern.

### A.2 Trice-Aufruf in einer Präprozessormakrodefinition

Beispiel:

```c
#define LOG_ERROR(x) trice("msg:error=%d\n", x)
```

**Anwendungsfall:** kurze projektspezifische Logging-Wrapper.

**Problem:** Der enthaltene Trice-Aufruf wird erst bei Expansion von `LOG_ERROR` verarbeitet. `__LINE__` und der aktive File Key können dann die Aufrufstelle beschreiben. Die bestehende `insert`-Semantik vergibt dagegen eine ID an der Definitionsstelle.

**Warum nicht im MVP:** Die Definitionsstellen-Semantik lässt sich mit dem direkten `File Key + __LINE__`-Mechanismus nicht allgemein herstellen. Ein automatischer Teil-`insert` würde die zentrale Eigenschaft des Bind-Workflows aufgeben.

**Praktische Lösung im MVP:** Wenn semantisch möglich, eine normale oder `static inline`-Funktion verwenden:

```c
static inline void logError(int x)
{
    trice("msg:error=%d\n", x);
}
```

**Spätere Lösung:** bind-fähiger Wrapperadapter, expliziter Kompatibilitätsmodus oder Präprozessoranalyse mit festgelegter Definitionsstellen-Semantik.

### A.3 Zusammengesetzter Formatstring

Beispiel:

```c
#define PREFIX "msg:"
trice(PREFIX "value=%d\n", value);
```

**Anwendungsfall:** Wiederverwendung von Textpräfixen oder makrogenerierte Meldungen.

**Problem:** Der bestehende Trice-Parser setzt statische, direkt erkennbare Formatstrings voraus. Allgemeine Makroverkettung erzeugt zusätzliche Fragen zu Präprozessorzustand, Identität und Listenstabilität.

**Warum nicht im MVP:** Diese Form ist bereits keine allgemeine zugesagte Insert-Funktionalität. Variable Inhalte sollen als Parameter übertragen werden, beispielsweise mit einer Trice-Stringvariante.

**Spätere Lösung:** keine allgemeine Zusage; nur klar begrenzte gemeinsame Parsererweiterung für Insert und Bind.

### A.4 Nicht transparenter Custom-Wrapper

Beispiel:

```c
#define MY_TRACE(x) trice("msg:value=%d\n", transform(x))
```

**Anwendungsfall:** projektspezifische Argumenttransformation oder fester Formatstring.

**Problem:** Dies ist kein bloßer Aliasname, sondern eine Makrodefinition mit eigener Semantik und einem Trice-Aufruf.

**Warum nicht im MVP:** `trice bind` unterstützt Aliase nur im selben Umfang wie `trice insert` und rekonstruiert keine beliebige User-Makrosemantik.

**Spätere Lösung:** expliziter Bind-Adapter oder Umstellung auf eine normale beziehungsweise `static inline`-Funktion.

### A.5 Explizite ID größer null

Beispiel:

```c
TRICE(ID(4711), "msg:fixed\n");
```

**Anwendungsfall:** bestehender Inserted-Source oder manuell festgelegte Legacy-ID.

**Problem im Bind-Projekt:** Die Stelle würde eine zweite ID-Quelle neben dem Sidecar einführen und die Target-Makro- sowie Konfliktbehandlung verkomplizieren.

**MVP-Verhalten:** projektweite Fehlerdiagnose mit Aufforderung, zunächst `trice clean` auszuführen.

**Alternative:** Projekt im klassischen Insert-Workflow belassen oder manuell vollständig zu Bind migrieren.

## Anhang B: Makro- und Alias-Abdeckungsmatrix

Vor dem Merge wird aus Target-Headern, gemeinsamem Parser und `_test/testdata/triceCheck.c` eine testbare Matrix erzeugt.

| Dimension | Werte beziehungsweise Beispiele |
|---|---|
| Case-Familie | `trice`, `Trice`, `TRice`, `TRICE` |
| Datenbreite | generisch, 8, 16, 32, optional 64 |
| Arity | variadisch, `_0`, `0`, `_1` bis unterstütztes Maximum |
| Bind-ID-Zustand | frei, `iD(0)`, `id(0)`, `Id(0)`, `ID(0)` |
| Negativzustand | explizite ID größer null |
| Spezialtyp | Standard, S, N, B, F, C, RPC/ABC, Assertions und Control-Flow-Helfer |
| Name | eingebaut, `-alias`, `-salias` im Insert-Umfang |
| Targetzustand | Inserted, Bind, Clean/Off |

Für jede als User-Level-Makro angebotene Kombination muss entweder:

- ein positiver Bind-Test existieren oder
- eine ausdrücklich dokumentierte Nichtunterstützung mit Negativtest vorliegen.

Ein Makro darf nicht allein deshalb aus der Bind-Unterstützung fallen, weil sein Name ausschließlich großgeschrieben, explizit aritätscodiert oder ein unterstütztes Sondermakro ist.

## Anhang C: Target-Makrodispatch und Präprozessorauflösung

### C.1 ID-freier lower-case Aufruf

Userdatei `module.c`:

```c
#include "trice.h"
#include "trice_module_c_K73A915E9C4021B8.h" // trice-bind

void f(void)
{
    trice("msg:Hello trice bind world\n"); // Zeile 9
}
```

Sidecar:

```c
#undef TRICE_SOURCE_KIND
#define TRICE_SOURCE_KIND TRICE_SOURCE_BOUND

#undef TRICE_FILE_KEY
#define TRICE_FILE_KEY K73A915E9C4021B8

#define TRICE_ID_K73A915E9C4021B8_L9 12345u
#define TRICE_BIND_HAS_TID_K73A915E9C4021B8_L9 0
#define TRICE_BIND_TID_K73A915E9C4021B8_L9 iD(12345u)
```

Expansion:

```text
TRICE_PUBLIC_SELECT(TRICE_SOURCE_BOUND, trice)("msg:Hello ...")
→ TRICE_PUBLIC_BOUND_trice("msg:Hello ...")
→ TRICE_BIND_0_trice("msg:Hello ...")
→ TRICE_EXISTING_TRICE_PATH(iD(12345u), "msg:Hello ...")
```

Der Compiler erhält dieselbe TID, die nach `trice insert` im Source gestanden hätte.

### C.2 ID-freies Uppercase-Makro

Usercode:

```c
TRICE8_3("msg:%d %d %d\n", a, b, c);
```

Bei:

```text
-defaultStampSize 16
```

enthält der Sidecar:

```c
#define TRICE_BIND_HAS_TID_K73A915E9C4021B8_L20 0
#define TRICE_BIND_TID_K73A915E9C4021B8_L20 Id(12346u)
```

Bei 0 beziehungsweise 32 wird `id(12346u)` beziehungsweise `ID(12346u)` erzeugt.

### C.3 Uppercase-Makro mit Null-Platzhalter

Usercode:

```c
TRICE8_3(ID(0), "msg:%d %d %d\n", a, b, c);
```

Sidecar:

```c
#define TRICE_BIND_HAS_TID_K73A915E9C4021B8_L24 1
#define TRICE_BIND_TID_K73A915E9C4021B8_L24 ID(12347u)
```

Target-Expansion:

```text
TRICE_PUBLIC_BOUND_TRICE8_3(ID(0), fmt, a, b, c)
→ TRICE_BIND_1_TRICE8_3(ID(0), fmt, a, b, c)
→ TRICE_EXISTING_TRICE8_3_PATH(ID(12347u), fmt, a, b, c)
```

Der vom User geschriebene Null-Platzhalter wird verworfen. Die vom Hostparser erkannte 32-Bit-Stamp-Form bleibt im Sidecar erhalten.

### C.4 Warum `TRICE(ID(0), "hi")` nicht im Target erkannt werden muss

Diese beiden Aufrufe besitzen jeweils zwei Userargumente:

```c
TRICE(ID(0), "msg:hi\n");
TRICE("msg:hi %d\n", x);
```

Eine reine Argumentzählung könnte sie nicht unterscheiden.

Der gemeinsame Hostparser kennt den Unterschied bereits und erzeugt:

```c
// erste Stelle
#define TRICE_BIND_HAS_TID_... 1
#define TRICE_BIND_TID_... ID(123u)

// zweite Stelle
#define TRICE_BIND_HAS_TID_... 0
#define TRICE_BIND_TID_... Id(124u) /* abhängig von defaultStampSize */
```

Der Target-Makropfad wählt anhand des Sidecar-Deskriptors, ob das erste Userargument verworfen werden muss. Es ist kein neues C-Präprozessor-Patternmatching auf `ID(0)` erforderlich.

### C.5 Inserted-Aufruf ohne Sidecar

Usercode:

```c
trice(iD(777), "msg:fixed\n");
```

Da kein Sidecar den lokalen Dispatch umstellt, gilt:

```text
TRICE_SOURCE_KIND = TRICE_SOURCE_INSERTED
```

Der bestehende User-Level-Makrovertrag verarbeitet `iD(777)` unverändert.

### C.6 Clean-/Off-Zustand

Bei:

```c
#define TRICE_CLEAN 1
```

wählt `trice.h` den bisherigen Clean-/Off-Pfad, bevor der Inserted-/Bind-Dispatch relevant wird.

Damit sind folgende Artefakte möglich:

```text
ID-freier Source + vorhandene Sidecars + TRICE_CLEAN == 1
```

Die Sidecars bleiben vorhanden, erzeugen aber keinen normalen aktiven Logging-Pfad.

### C.7 Warum ein Hash der Trice-Zeile die erneute Bindung nicht ersetzt

Ein Generator könnte einen Hash des Sourcetextes in einen Sidecar-Makronamen schreiben. Der unveränderte C-Präprozessoraufruf kennt diesen Hash jedoch nicht. Standardkonform kann er an der Aufrufstelle nur bereits verfügbare Tokens wie File Key und `__LINE__` zusammensetzen.

Verschiebt sich eine Logstelle, erzeugt `__LINE__` einen anderen Makronamen. Deshalb muss der Sidecar neu erzeugt werden. Die numerische ID bleibt durch `til.json` und `li.json` stabil.

## Anhang D: Kurzreferenz Migration und Zustände

### Insert zu Bind

```text
trice clean
trice bind
Build
```

- IDs werden aus User-Trice-Aufrufen entfernt.
- Sidecar-Includes und Sidecars werden erzeugt.
- Vorhandenes `TRICE_CLEAN` wird durch `bind` auf `0` gesetzt.

### Normaler Bind-Betrieb

```text
trice bind
Build
```

### Bind plus `trice clean`, `TRICE_CLEAN` vorhanden

```text
TRICE_CLEAN: 0 → 1
Source und Sidecars bleiben
Build wird Clean/Off
```

### Bind plus `trice clean`, `TRICE_CLEAN` fehlt

```text
Source und Sidecars bleiben
keine Konfigurationsänderung
Bind-Build bleibt aktiv
```

### Bind zu Insert

```text
Sidecar-Includes manuell entfernen
generierte Sidecars optional löschen
trice insert
Build
```
